## B2 — valori giusti, ordine sbagliato

**Cosa hai scritto:** `{ email: 'a', password: 'b' }` e, nella Verifica, `Sì`.

**Cosa fa davvero, passo passo:**
1. `{ [name]: 'X', ...}`: `name` vale `'password'`, quindi la **prima** chiave creata è `password: 'X'`.
   L'oggetto ora è `{ password: 'X' }`.
2. `...fields` copia `email: 'a'`. È una chiave nuova, quindi va **in fondo**: `{ password: 'X', email: 'a' }`.
3. `...fields` copia `password: 'b'`. La chiave esiste già, quindi cambia solo il **valore** e la posizione resta la stessa:
   `{ password: 'b', email: 'a' }`.

**Output reale:** `{ password: 'b', email: 'a' }`

**L'idea sbagliata dietro.** Pensavi che sovrascrivere una chiave la spostasse, come se il risultato
fosse "una copia di `fields`".

**L'idea giusta.** Una chiave occupa il suo posto **dalla prima volta che nasce**. Le scritture successive
cambiano il contenuto, non la posizione. È come una sedia a teatro: chi arriva dopo con lo stesso biglietto
si siede al posto di chi c'era, non in un posto nuovo in fondo alla fila.

**Sulla Verifica.** Il tuo output reale (`{password: 'b', email: 'a'}`) **è diverso** dalla tua previsione,
eppure hai scritto "Sì". Il perché è giusto: hai capito la regola "vince l'ultima", e lo conferma il registro.
L'output no.

**Domanda guida.** Se il codice fosse `{ ...fields, [name]: 'X' }`, quale sarebbe l'ordine delle chiavi e
quale il valore di `password`?

## B3 — contenuto giusto, formato sbagliato, verifica non eseguita

**Output reale (Node):** `Email [ 'type', 'value', 'required' ]`
Nella console di Chrome: `Email (3) ['type', 'value', 'required']`.

Hai capito **cosa** finisce in `rest`. Ma l'"output reale" che hai scritto, `Email, [type, value, required]`,
è identico alla tua previsione, con la virgola dopo `Email` e senza apici. Nessun ambiente stampa così.
Vuol dire che non l'hai copiato dal terminale. Se l'hai eseguito, hai ricopiato la previsione; se non
l'hai eseguito, la Verifica non è stata fatta. In entrambi i casi la Verifica non è valida.

**Il perché è superficiale.** "label stampa il valore e Object.keys le chiavi" descrive il `console.log`,
non la parte importante, cioè il **destructuring con rest**:
1. La funzione riceve `{ label: 'Email', type: 'email', value: '', required: true }`.
2. `{ label, ...rest }` estrae `label` in una variabile.
3. `...rest` raccoglie **tutte le altre** proprietà in un oggetto nuovo:
   `rest = { type: 'email', value: '', required: true }`. `label` lì dentro non c'è.
4. `Object.keys(rest)` restituisce un **array di stringhe**: `['type', 'value', 'required']`.

**Domanda guida.** Cosa stamperebbe `console.log(label, rest)` invece di `Object.keys(rest)`?
E perché questo pattern è utile nel tuo `FormInput`, che riceve `label` e poi passa `{...otherProps}` all'`<input>`?

## B4 — sbagliato, e la previsione contraddice il perché

**Cosa hai scritto:** `A B C D E F`, cioè l'ordine del codice scritto.
**Il tuo perché:** "prima il codice sincrono, poi i microtask, poi il resto". **La regola è giusta**,
ma la previsione non la applica. È la terza consegna in cui spiegazione e output si contraddicono.

**Cosa fa davvero, con tre colonne:**

| Passo | Cosa succede | Stampa | Coda microtask | Coda task |
|---|---|---|---|---|
| 1 | `console.log('A')` | **A** | | |
| 2 | `setTimeout(...)` → mette B tra i **task** | | | B |
| 3 | parte la funzione async, `console.log('C')` | **C** | | B |
| 4 | `await` → sospende la funzione; il resto (D) va nei **microtask** | | D | B |
| 5 | `.then(...)` → E va nei **microtask** | | D, E | B |
| 6 | `console.log('F')` | **F** | D, E | B |
| 7 | finisce il codice sincrono, si svuotano i microtask in ordine | **D**, **E** | | B |
| 8 | solo dopo, un task | **B** | | |

**Output reale:** `A C F D E B`, una lettera per riga.

**Due idee sbagliate:**
- "Il codice di una funzione async è tutto asincrono." No: fino al primo `await` gira **sincrono**,
  per questo C esce subito dopo A.
- "`setTimeout(..., 0)` vuol dire subito." No: `0` vuol dire "appena possibile, **dopo** i microtask".

**E l'`undefined`?** Non viene dal tuo codice. Quando scrivi nella **console** del browser, dopo
aver eseguito il codice Chrome mostra il **valore dell'ultima istruzione**. L'ultima è `console.log('F')`,
e `console.log` restituisce `undefined`. Non è una stampa: è la console che ti dice "il risultato è
undefined". Con `node -e` non compare. Quindi nell'output reale **non va scritto**.

**Sulla Verifica.** "Forse… dovrebbe essere giusta": la tua previsione aveva B al secondo posto, quello
reale è all'ultimo. Era sbagliata, e andava scritto **No** con l'idea sbagliata.

**Domanda guida.** Se aggiungi `console.log('G')` subito dopo `console.log('D')`, dentro la funzione
async, dove appare G? Riempi le tre colonne prima di rispondere.

## B5 — sbagliato su un valore, e non eseguito

**Cosa hai scritto:** `10, undefined, null, 0`. Nella Verifica l'output reale è vuoto, ma c'è scritto "sì".
**Output reale:** `10 10 null 0`

**Cosa fa davvero, passo passo:**
1. `g()` → nessun argomento, quindi `x` è `undefined` → scatta il default → **10**.
2. `g(undefined)` → passare `undefined` è **la stessa cosa** che non passare niente → default → **10**.
3. `g(null)` → `null` è un valore vero e proprio ("vuoto di proposito") → niente default → **null**.
4. `g(0)` → `0` è un numero → niente default → **0**.

**L'idea sbagliata dietro.** "Se passo `undefined`, x vale `undefined`." Il parametro di default non
controlla **se** hai passato qualcosa: controlla **se il valore è `undefined`**. Questo era scritto
nell'aiuto 3 del Lab: "Default: scatta solo con undefined".

**L'idea giusta.** `undefined` = "nessuno ha messo niente qui", quindi JavaScript usa il default.
`null` = "qualcuno ha deciso che qui non c'è niente", quindi JavaScript rispetta la scelta.
È la stessa differenza tra un modulo con un campo **lasciato in bianco** e uno con scritto "nessuno".

**Domanda guida.** Con `const h = ({ size = 'M' } = {}) => size;`, cosa restituiscono `h()`,
`h({})`, `h({ size: null })`, `h({ size: undefined })`?

## B6 — nessuna previsione (ma onesta)

Hai scritto "non riesco a immaginare cosa succede" invece di inventare: **è il comportamento giusto**.
Ma così il blocco non conta come risposta. Ecco il ragionamento passo passo.

**Output reale:**
```text
ok
Uncaught (in promise) Error: boom
```
(L'`undefined` in mezzo è di nuovo la console del browser, come in B4.)

**Cosa fa davvero, passo passo:**
1. `load` è `async`. Una funzione async **non lancia mai l'errore a chi la chiama**: restituisce sempre
   una **Promise**. Se dentro c'è un `throw`, la Promise viene **rifiutata** (rejected).
2. `load()` viene chiamata **senza `await`**. Il `try` riceve una Promise rifiutata e la ignora, perché per il `try`
   una Promise è un oggetto qualsiasi, non un errore. Nessuna eccezione, quindi il `catch` non scatta.
3. `console.log('ok')` → **ok**. `'preso'` non verrà mai stampato.
4. Il `try/catch` finisce. Più tardi JavaScript si accorge che c'è una Promise rifiutata che nessuno ha gestito
   (nessun `await`, nessun `.catch`) e lo segnala: **Uncaught (in promise) Error: boom**.
   In Node lo script si interrompe con un errore.

**L'idea giusta.** Un `try/catch` cattura solo gli errori che arrivano **mentre è in esecuzione**.
Un errore dentro una Promise arriva "per posta" più tardi. Per riceverlo nel `catch` devi **aspettarlo**:
`await load();`, dentro una funzione async. È come un pacco con dentro una bomba: se non apri il pacco
(`await`), il `try` non sa nemmeno che c'è. Esplode dopo, quando nessuno è nella stanza.

**Perché ti serve.** È lo stesso schema di `signInAuthUserWithEmailAndPassword` nel tuo `sign-in-form`:
se togli l'`await`, l'errore `auth/invalid-credential` non arriva mai al tuo `catch`.

**Domanda guida.** Cambia solo la riga 3 in `await load();` e metti tutto dentro `(async () => { ... })();`.
Cosa stampa adesso? `ok` compare?
