1Il problema: due componenti lontani, un dato in comune

Dopo il login, SignInForm conosce l'utente. Navigation deve mostrare "SIGN OUT" invece di "SIGN IN". Guarda dove stanno nell'albero:

Senza Context, lo state dovrebbe stare nel primo antenato comune (App) e scendere come prop attraverso componenti che non lo usano, come Routes e Authentication. Questo è il prop drilling. Con React Router è ancora peggio: le route ricevono element={<Authentication />} e passare props attraverso <Outlet /> è scomodo.

Cosa risolve il Context, e cosa no Il Context risolve il trasporto: chiunque sotto il Provider legge il valore senza intermediari. Non è un sistema di stato: lo state continua a vivere in un normale useState, dentro il componente Provider. Il Context è il cavo, non la batteria.

2Teoria e terminologia

I tre pezzi

PezzoCodiceCosa fa
Creazioneconst UserContext = createContext(defaultValue)Crea l'oggetto context, una specie di "canale". Si fa una volta, a livello di modulo, fuori dai componenti. L'oggetto in sé non contiene dati.
Fornitura<UserContext.Provider value={value}>Dice: "per tutti i componenti qui sotto, il valore di questo canale è value". Questo è il Provider.
Letturaconst value = useContext(UserContext)Restituisce il value del Provider più vicino sopra. In più, iscrive il componente: quando quel value cambia, il componente fa re-render. Chi lo chiama è un consumer.

Il valore di default: l'ultima spiaggia

defaultValue viene usato solo quando non c'è nessun Provider sopra il componente che legge. Non è il valore iniziale dello state, che invece è useState(null) dentro il Provider. Nel corso:

export const UserContext = createContext({
  setCurrentUser: () => null,   // funzione "finta": non fa niente
  currentUser: null,
});

Dichiarare la forma del valore (le stesse chiavi del vero value) serve a due cose: documenta cosa offre il context, e fa sì che un componente fuori dal Provider non vada in crash. Il prezzo è che fallisce in silenzio: setCurrentUser(user) non fa niente e non dà nessun errore. Ci torniamo negli errori tipici.

La regola dei re-render

  1. Il componente Provider (UserProvider) ha uno state. Quando lo state cambia, il Provider fa re-render.
  2. A ogni render del Provider, const value = { currentUser, setCurrentUser } crea un nuovo oggetto.
  3. React confronta il value vecchio con quello nuovo usando Object.is, cioè per riferimento. È un oggetto nuovo, quindi è "cambiato".
  4. Tutti i consumer di quel context fanno re-render, e con loro i figli che disegnano direttamente.
  5. I componenti che non leggono il context e che arrivano come children dall'esterno non fanno re-render.
Il punto 5 è sottile ma importantissimo UserProvider riceve <App /> come children. L'elemento <App /> è stato creato in index.js, non dentro UserProvider. Quando UserProvider fa re-render, restituisce lo stesso identico elemento children, e React lo salta. È per questo che il pattern ({ children }) => <Ctx.Provider>{children}</Ctx.Provider> è efficiente: fa re-render solo chi legge davvero.

useEffect e il listener di Firebase

onAuthStateChanged è un observer: invece di chiedere "chi è loggato?" una volta, ti iscrivi e Firebase ti avvisa ogni volta che lo stato cambia (login, logout, sessione ripristinata al refresh). Un'iscrizione si fa una volta e va chiusa quando non serve più:

useEffect(() => {
  const unsubscribe = onAuthStateChangedListener(callback);  // iscriviti
  return unsubscribe;                                        // cleanup: disiscriviti
}, []);                                                      // [] = solo al montaggio
  • Perché useEffect? Iscriversi è un effetto collaterale, cioè parla con il mondo esterno. Se lo facessi nel corpo del componente, ti iscriveresti a ogni render.
  • Perché []? L'array delle dipendenze vuoto vuol dire "esegui dopo il primo render e mai più".
  • Perché return unsubscribe? La funzione restituita da un effect è il cleanup: React la chiama quando il componente viene smontato. Senza cleanup il listener resta vivo e chiama setCurrentUser su un componente che non esiste più.
StrictMode e la tua versione di React Il tuo index.js usa <React.StrictMode> con React 17.0.2. In React 17, StrictMode (solo in sviluppo) esegue due volte il corpo dei componenti per scovare effetti collaterali nel render, ma non gli effect. Da React 18 in poi, StrictMode esegue anche gli effect due volte (montaggio → cleanup → montaggio), apposta per verificare che il tuo cleanup funzioni. Se un giorno aggiorni React e vedi due iscrizioni nei log, è questo: con un cleanup corretto non succede niente di male.

3Modello mentale: la stazione radio

📻
createContext sceglie una frequenza (per esempio 101.5 FM, "UserContext"). Da sola la frequenza non trasmette niente.
Il Provider è un'antenna che trasmette su quella frequenza il suo value in quel momento. Copre solo il territorio sotto di sé.
useContext è una radio sintonizzata su quella frequenza: sente l'antenna più vicina sopra di lei. E quando l'antenna cambia trasmissione, la radio si riaccende (re-render).
Il default è il fruscio che senti se sei fuori da ogni copertura.
Chi non ha la radio (non chiama useContext) non sente niente e non viene disturbato.

export const UserContext = createContext({
  setCurrentUser: () => null,
  currentUser: null,

export const UserProvider = ({ children }) => {
  const [currentUser, setCurrentUser] = useState(null);

5Forma dei dati

UserContext (l'oggetto creato da createContext, semplificato)
value trasmesso dal Provider dopo il login
Cosa restituisce useContext in un componente fuori dal Provider
Il valore di ritorno di onAuthStateChanged
Due render, due oggetti diversi render 1: value = { currentUser: null, setCurrentUser: ƒ }
render 2: value = { currentUser: null, setCurrentUser: ƒ }
Il contenuto è identico, ma render1.value === render2.value è false: sono due oggetti creati in due momenti diversi. React confronta i riferimenti, non il contenuto. setCurrentUser invece è lo stesso riferimento in ogni render: React garantisce che la funzione setter di useState sia stabile.

Il corso costruisce UserContext in due passi. Capire perché si passa dalla v1 alla v2 è più importante del codice stesso.

v2 · lezione 11: un unico listener nel Provider

// user.context
useEffect(() => {
  const unsubscribe = onAuthStateChangedListener((user) => {
    if (user) createUserDocumentFromAuth(user);
    setCurrentUser(user);
  });
  return unsubscribe;
}, []);

// sign-in-form: nessun setCurrentUser
await signInWithGooglePopup();
Problema della v1Come lo risolve la v2
Ogni punto che cambia l'utente (Google, email, sign-up, sign-out) deve ricordarsi di chiamare setCurrentUser. Se ne dimentichi uno, UI e realtà divergono.C'è una sola fonte di verità: Firebase. Il Provider ascolta e si allinea, qualunque sia il modo in cui l'utente è entrato o uscito.
Al refresh della pagina currentUser torna null, anche se Firebase ha ancora la sessione salvata. Risultato: un "SIGN IN" falso.Al montaggio, il listener riceve subito l'utente della sessione ripristinata.
Ogni componente deve importare il context solo per scriverci.I form non conoscono più il context: fanno login e basta. Meno dipendenze.
createUserDocumentFromAuth viene chiamata in più punti.Viene chiamata in un posto solo, a ogni login. È idempotente (M3), quindi è sicuro.

Il file completo, annotato

import { createContext, useState, useEffect } from 'react';

import {
  onAuthStateChangedListener,
  createUserDocumentFromAuth,
} from '../utils/firebase/firebase.utils';

export const UserContext = createContext({
  setCurrentUser: () => null,
  currentUser: null,
});

export const UserProvider = ({ children }) => {
  const [currentUser, setCurrentUser] = useState(null);
  const value = { currentUser, setCurrentUser };

  useEffect(() => {
    const unsubscribe = onAuthStateChangedListener((user) => {
      if (user) {
        createUserDocumentFromAuth(user);
      }
      setCurrentUser(user);
    });

    return unsubscribe;
  }, []);

  return <UserContext.Provider value={value}>{children}</UserContext.Provider>;
};
  1. Il context importa le funzioni di utils, non l'SDK: la separazione dei livelli (M3 ⑦) resta intatta.
  2. Creazione a livello di modulo: l'oggetto viene creato una volta, quando il file viene importato. Se lo creassi dentro un componente, ogni render produrrebbe un context diverso e nessuno si sintonizzerebbe.
  3. Destructuring delle props: children è tutto quello che metti tra <UserProvider> e </UserProvider>.
  4. La batteria: lo state vero. null = "nessuno loggato" (o "non lo so ancora": vedi le domande da dev).
  5. Nuovo oggetto a ogni render. Ok per questa app; nella sezione ⑧ vedi come la doc lo ottimizza.
  6. Effetto con cleanup: iscrizione al primo render, disiscrizione allo smontaggio.
  7. Fire-and-forget: nessun await. La scrittura in Firestore parte, ma setCurrentUser non la aspetta: la UI si aggiorna subito.
  8. Fuori dall'if: viene chiamata sia con un utente sia con null (logout).
  9. Restituisce la funzione, non la chiama: return unsubscribe, non return unsubscribe().
  10. Sintassi React 17: .Provider. Il value è quello che ricevono i consumer.

CartContext (lezioni 13–16): stato e azioni

const addCartItem = (cartItems, productToAdd) => {
  const existingCartItem = cartItems.find(
    (cartItem) => cartItem.id === productToAdd.id
  );
  if (existingCartItem) {
    return cartItems.map((cartItem) =>
      cartItem.id === productToAdd.id
        ? { ...cartItem, quantity: cartItem.quantity + 1 }
        : cartItem
    );
  }
  return [...cartItems, { ...productToAdd, quantity: 1 }];
};

// nel Provider:
const addItemToCart = (productToAdd) =>
  setCartItems(addCartItem(cartItems, productToAdd));
Il pattern da riconoscere La logica (addCartItem) è una funzione pura fuori dal componente: riceve l'array vecchio e ne restituisce uno nuovo, senza modificarlo. Il Provider espone solo l'azione (addItemToCart), e i componenti non sanno com'è fatto l'array. È lo stesso principio di firebase.utils.js: chi usa non deve sapere come funziona dentro.

React: createContext e useContext

Le pagine di riferimento sono react.dev › createContext e react.dev › useContext. Sono pagine di Reference (T1 ②): le leggi con Syntax → Returns → Caveats.

La doc dice (riassunto)Cosa vuol dire per il tuo codice
createContext › Returns: l'oggetto context "does not hold any information". Rappresenta quale context si legge o si fornisce.Il canale non è il dato. Il dato sta nello useState del Provider.
defaultValue: è il valore usato quando non c'è nessun Provider sopra. È un fallback di "ultima spiaggia", statico, che non cambia mai.Non è lo stato iniziale. setCurrentUser: () => null del default non aggiornerà mai niente.
useContext › Returns: il value del Provider più vicino sopra; se non c'è, il defaultValue. React fa re-render dei componenti che leggono un context quando questo cambia.È il meccanismo di iscrizione che hai visto nel simulatore.
Caveat 1: useContext() non vede i Provider restituiti dallo stesso componente; il Provider deve stare sopra.Dentro UserProvider non puoi fare useContext(UserContext) e aspettarti il value che lui stesso fornisce.
Caveat 2: re-render di tutti i figli che usano il context, a partire dal Provider che riceve un value diverso; il confronto usa Object.is; memo non impedisce di ricevere il valore nuovo.Un nuovo oggetto value a ogni render del Provider vuol dire che tutti i consumer fanno re-render.
Attenzione alla versione: la doc è più avanti di te

react.dev documenta React 19. Lì il Provider si scrive <SomeContext value={…}>, e la doc dice che SomeContext.Provider è il modo "legacy", quello usato prima di React 19. Tu hai React 17.0.2 (controlla package.json): devi usare <SomeContext.Provider value={…}>. Se copi la forma nuova in React 17, il context non funziona.

Regola da T1: prima di copiare, controlla la versione, sia della libreria (package.json) sia della doc (react.dev = ultima versione).

Ottimizzare il value: lo snippet della doc tradotto per React 17

DOC useContext › Optimizing re-renders

function MyApp() {
  const [currentUser, setCurrentUser] = useState(null);

  const login = useCallback((response) => {
    storeCredentials(response.credentials);
    setCurrentUser(response.user);
  }, []);

  const contextValue = useMemo(() => ({
    currentUser,
    login
  }), [currentUser, login]);

  return (
    <AuthContext value={contextValue}>
      <Page />
    </AuthContext>
  );
}

TRADOTTO sul tuo UserProvider, React 17

export const UserProvider = ({ children }) => {
  const [currentUser, setCurrentUser] = useState(null);

  // stesso oggetto finché currentUser non cambia
  const value = useMemo(
    () => ({ currentUser, setCurrentUser }),
    [currentUser]
  );

  // ...useEffect invariato

  return (
    <UserContext.Provider value={value}>
      {children}
    </UserContext.Provider>
  );
};

Tabella di traduzione: AuthContext → UserContext; <AuthContext value> → <UserContext.Provider value> (versione!); login con useCallback → non serve, perché setCurrentUser è già stabile; <Page /> → {children}. Ti serve davvero? Nel corso no: UserProvider fa re-render solo quando cambia lo state, e in quel caso il value deve cambiare comunque. useMemo conta quando il Provider fa re-render per altri motivi, per esempio quando il suo genitore fa re-render.

CORSO

// firebase.utils.js
export const onAuthStateChangedListener = (callback) =>
  onAuthStateChanged(auth, callback);

// user.context.jsx
const unsubscribe = onAuthStateChangedListener((user) => {
  if (user) {
    createUserDocumentFromAuth(user);
  }
  setCurrentUser(user);

Snippet di Firebase (Google), licenza Apache 2.0.

  • Lo snippet ignora il valore di ritorno. La reference però dice che onAuthStateChanged restituisce Unsubscribe, una funzione. In uno script si può ignorare; in un componente React che si monta e si smonta no: è proprio quello che useEffect deve restituire.
  • Il ramo else della doc (utente uscito) nel corso non c'è, perché setCurrentUser(user) sta fuori dall'if e gestisce entrambi i casi con una riga sola.
  • Firma della reference: onAuthStateChanged(auth, nextOrObserver, error?, completed?): Unsubscribe. Leggendo i parametri scopri che error e completed sono deprecati: "This callback is never triggered". Gli errori di login e logout si intercettano sulle Promise di signIn… e signOut. Senza la reference, potresti aspettarti errori che non arriveranno mai.
  • Perché un observer e non auth.currentUser? La guida spiega che, usando l'observer, l'oggetto Auth non è in uno stato intermedio, come l'inizializzazione, quando leggi l'utente. Al caricamento della pagina, auth.currentUser può valere null solo perché Firebase non ha ancora finito di ripristinare la sessione.

9Errori tipici: dal modello sbagliato a quello giusto

❶ "useContext funziona ovunque"

// index.js dimenticato: <App /> NON è dentro <UserProvider>
const { setCurrentUser } = useContext(UserContext);
setCurrentUser(user);   // nessun errore… e nessun effetto

Passo per passo: nessun Provider sopra → useContext restituisce il default → setCurrentUser è () => null → viene chiamata, restituisce null, fine. La Navigation non cambia mai, la console non dice niente.

Modello sbagliato"Se importo il context, sono collegato."
Modello giusto"Sono collegato solo se un Provider sta sopra di me nell'albero. Importare il file non collega niente."

❷ "Modifico l'array dello state, tanto è lo stesso"

const addItemToCart = (product) => {
  cartItems.push({ ...product, quantity: 1 });  // modifica l'array esistente
  setCartItems(cartItems);                       // stesso riferimento!
};

Passo per passo: push modifica l'array che React ha già in memoria. setCartItems(cartItems) passa lo stesso riferimento, React fa Object.is(vecchio, nuovo) → true → "niente è cambiato" → nessun re-render. Il carrello contiene il prodotto, ma l'icona continua a mostrare 0.

Modello sbagliato"React guarda il contenuto."
Modello giusto"React guarda il riferimento. Per dirgli 'è cambiato' gli do un oggetto o array nuovo (spread, map, filter)."

❸ "Il listener si chiude da solo"

useEffect(() => {
  onAuthStateChangedListener((user) => setCurrentUser(user));
}, []);   // manca: return unsubscribe

Oggi UserProvider vive per tutta la durata dell'app, quindi il danno non si vede. Ma lo stesso pattern dentro un componente che si monta e smonta (una pagina, un modale) accumula un listener in più a ogni montaggio. In React 18 con StrictMode lo vedresti subito: due listener attivi.

Modello sbagliato"Quando il componente sparisce, sparisce tutto quello che ha creato."
Modello giusto"Sparisce solo ciò che appartiene a React. Le iscrizioni a sistemi esterni (Firebase, timer, eventi) vanno chiuse a mano nel cleanup."

❹ "Ogni dato che si calcola va messo nello state"

// corso, lezioni 15-16
const [cartCount, setCartCount] = useState(0);
useEffect(() => {
  setCartCount(cartItems.reduce((total, item) => total + item.quantity, 0));
}, [cartItems]);

Passo per passo: cartItems cambia → render (con cartCount ancora vecchio!) → l'effect calcola → setCartCount → secondo render con il valore giusto. Due render invece di uno, e un istante in cui i due dati non sono coerenti tra loro.

// alternativa: dato DERIVATO, calcolato durante il render
const cartCount = cartItems.reduce((total, item) => total + item.quantity, 0);
Modello sbagliato"Tutto ciò che mostro deve essere state."
Modello giusto"Lo state è il minimo indispensabile. Ciò che si può calcolare da altro state è derivato: si calcola al volo. La doc di React ne parla nella pagina 'You Might Not Need an Effect'."

Il corso lo fa con useEffect per insegnarti useEffect. Non è un errore grave, ma un dev deve saper vedere l'alternativa.

❺ "Il default e il value si allineano da soli"

// default del CartContext (corso, lezione 16)
removeItemFromCart: () => {},
// value del CartProvider
removeItemToCart,    // ← nome diverso!

Un componente che fa const { removeItemFromCart } = useContext(CartContext) riceve undefined dal Provider vero, perché quella chiave non esiste nel value. Al click: TypeError: removeItemFromCart is not a function. Il default non protegge, perché c'è un Provider sopra e quindi il default non viene usato.

Modello sbagliato"Il default descrive cosa c'è nel context."
Modello giusto"Il default è solo un fallback. Ciò che i consumer ricevono è esattamente l'oggetto value, chiave per chiave."
