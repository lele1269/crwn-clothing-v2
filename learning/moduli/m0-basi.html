1Il problema: leggere codice che "sembra" chiaro

Questa riga del tuo handleChange contiene quattro concetti diversi:

setFormFields({ ...formFields, [name]: value });
  • { … }: un oggetto nuovo, cioè un nuovo riferimento. È per questo che React se ne accorge.
  • ...formFields: lo spread, che copia (in superficie) tutte le chiavi.
  • [name]: value: una computed property, cioè una chiave decisa a runtime.
  • setFormFields(…): chiede un re-render. Non cambia formFields subito.

Se anche uno solo di questi pezzi è sfocato, il codice funziona finché non smette, e a quel punto non sai dove guardare. Questo modulo li mette a fuoco uno per uno.

C · Le funzioni sono valori

const signOutUser = async () => await signOut(auth);

onClick={signOutUser}     // passi la FUNZIONE: React la chiamerà al click
onClick={signOutUser()}   // la CHIAMI subito, durante il render, e passi il risultato (una Promise)

Una funzione può essere passata, salvata e restituita come qualsiasi altro valore. È quello che succede con onChange={handleChange}, con le callback di onAuthStateChanged e con return unsubscribe. Una funzione definita dentro un componente ricorda le variabili del render in cui è nata: si chiama closure.

D · Codice asincrono

TermineSignificato
PromiseUn oggetto che rappresenta un risultato futuro. Ha tre stati: pending (in attesa), fulfilled (risolta con un valore), rejected (rifiutata con un errore).
async functionUna funzione che restituisce sempre una Promise, anche se dentro fai return 5.
awaitSospende solo la funzione async in cui si trova finché la Promise non si risolve. Se la Promise viene rifiutata, await lancia l'errore su quella riga.
try/catch + awaitIntercetta gli errori delle Promise, ma solo se c'è await.
.then(fn).catch(fn)Lo stesso meccanismo scritto con le callback. La documentazione di Firebase lo usa spesso.
Promise.all([p1, p2])Aspetta più Promise in parallelo. Se una viene rifiutata, il tutto viene rifiutato.
Event loopIl meccanismo che decide quando eseguire il codice in attesa: prima finisce il codice sincrono, poi le microtask (Promise), poi le task (setTimeout, eventi).

E · Il ciclo di render di React

  1. Un componente è una funzione che React chiama per sapere cosa disegnare.
  2. useState restituisce [valoreDiQuestoRender, setter].
  3. Il setter non cambia la variabile: chiede a React un nuovo render, in cui useState restituirà il valore nuovo.
  4. Dentro un render, lo state è una fotografia fissa. setCount(count + 1); console.log(count) stampa il valore vecchio.
  5. Dopo il render, React aggiorna il DOM ed esegue gli effect.

6Nel tuo codice

const handleChange = (event) => {
  const { name, value } = event.target;

  setFormFields({ ...formFields, [name]: value });
};

const handleSubmit = async (event) => {
  event.preventDefault();

  try {
    const { user } = await createAuthUserWithEmailAndPassword(
      email,
      password
    );
    await createUserDocumentFromAuth(user, { displayName });
    resetFormFields();
  } catch (error) {
    // ...
  }
};

const FormInput = ({ label, ...otherProps }) => (
  <input className='form-input' {...otherProps} />
);
  1. Funzione come valore: handleChange viene passata a onChange, e la chiamerà React.
  2. Destructuring: estrae name (l'attributo dell'input) e value (il testo attuale).
  3. Oggetto nuovo + spread + computed property. Se l'utente scrive nell'input name="email": { ...formFields, email: 'l' }.
  4. async: handleSubmit restituisce una Promise, che React ignora.
  5. await + destructuring: aspetta il UserCredential e ne estrae user.
  6. try/catch con await: qualunque Promise rifiutata sopra arriva al catch.
  7. Rest nei parametri: label a parte, tutto il resto (type, name, value, onChange, required) in otherProps.
  8. Spread nelle props JSX: equivale a scrivere a mano type={…} name={…} value={…} ….

8Doc ufficiale: .then contro async/await

La documentazione di Firebase usa spesso .then().catch(), il corso usa async/await. Sono lo stesso meccanismo scritto in due modi.

DOC Password Authentication

createUserWithEmailAndPassword(auth, email, password)
  .then((userCredential) => {
    // Signed up
    const user = userCredential.user;
    // ...
  })
  .catch((error) => {
    const errorCode = error.code;
    const errorMessage = error.message;
    // ..
  });

TRADUZIONE async/await

try {
  const userCredential = await createUserWithEmailAndPassword(
    auth, email, password
  );
  const user = userCredential.user;   // oppure: const { user } = await …
  // ...
} catch (error) {
  const errorCode = error.code;
  const errorMessage = error.message;
  // ..
}
.then / .catchasync / await
il parametro di .then((x) => …)il valore di const x = await …
il corpo di .thenle righe dopo l'await
.catch((error) => …)catch (error) { … }, solo per le righe dentro il try
il codice dopo la catena parte subitoil codice dopo await aspetta

9Errori tipici

❶ "Ho copiato l'oggetto, quindi è indipendente"

const copia = { ...user };
copia.address.city = 'Roma';
user.address.city;   // 'Roma' ← address è condiviso
Modello sbagliato"Lo spread clona tutto."
Modello giusto"Lo spread copia un livello. Ogni oggetto annidato che modifico va copiato a sua volta."

❷ "forEach aspetta gli await"

ids.forEach(async (id) => {
  await deleteUserDocument(db, id);
});
console.log('fatto');   // stampato PRIMA che le cancellazioni finiscano

forEach chiama la callback e ignora la Promise che restituisce. Usa for (const id of ids) await … se le vuoi in sequenza, oppure await Promise.all(ids.map(…)) se le vuoi in parallelo.

Modello sbagliato"await dentro un ciclo fa aspettare il ciclo."
Modello giusto"await fa aspettare la funzione in cui si trova. Se quella funzione è una callback, aspetta solo la callback."

❸ "Dopo setState il valore è aggiornato"

setFormFields({ ...formFields, email: 'x' });
console.log(formFields.email);   // valore VECCHIO
Modello sbagliato"setState assegna la variabile."
Modello giusto"setState prenota un render nuovo. La variabile di questo render non cambierà mai."

❹ "try/catch prende tutto"

try {
  createUserDocumentFromAuth(user);   // senza await
} catch (e) {
  // non arriva MAI qui per errori di Firestore
}

Il try finisce prima che la Promise venga rifiutata. L'errore diventa un "Uncaught (in promise)".
