Modulo 4 · Form controllati

Il form come riflesso dello state

Ogni tasto premuto fa un giro completo: evento → handler → nuovo state → re-render → input aggiornato. Capire questo giro è ciò che separa "il form funziona" da "so perché funziona".

1Il problema: due fonti di verità

Un <input> HTML ha già un suo stato: il testo che contiene, gestito dal browser. Se anche React tiene una copia di quel testo, ci sono due versioni dello stesso dato. Quale vince? Un componente controllato risolve il conflitto in modo netto: React è l'unica fonte di verità, e l'input mostra sempre e solo ciò che c'è nello state.

I pezzi del tuo form

  • Uno state a oggetto per tutti i campi: { displayName, email, password, confirmPassword }.
  • Un solo handler per tutti gli input: legge event.target.name e aggiorna quella chiave con una computed property (M0).
  • L'attributo name di ogni input deve essere uguale alla chiave nello state: è il "cavo" che li collega.
  • Il submit arriva su <form onSubmit> (non sul click del bottone). event.preventDefault() impedisce al browser di ricaricare la pagina.
  • required, type="email": validazione nativa del browser, che blocca il submit prima che parta il tuo handler.
  • Evento sintetico: React ti passa un SyntheticEvent che avvolge quello nativo. Da React 17 non c'è più l'"event pooling": puoi leggere event.target anche dopo un await. Le buone abitudini però restano: estrai subito ciò che ti serve.

3Modello mentale: lo specchio

🪞
L'input è uno specchio dello state. Quando premi un tasto, non stai scrivendo nello specchio: stai chiedendo a React di cambiare l'originale (lo state). React cambia l'originale, ridisegna, e lo specchio mostra il nuovo riflesso. Se l'handler non aggiorna lo state, lo specchio mostra di nuovo il vecchio riflesso: sembra che la tastiera non funzioni.

4Flusso animato e laboratorio

const SignUpForm = () => {
  const [formFields, setFormFields] = useState(defaultFormFields);
  const { displayName, email, password, confirmPassword } = formFields;

  const handleChange = (event) => {
    const { name, value } = event.target;
    setFormFields({ ...formFields, [name]: value });
  };

  return (
    <FormInput label='Email' type='email' required
      onChange={handleChange} name='email' value={email} />
  );
};

const FormInput = ({ label, ...otherProps }) => (
  <div className='group'>
    <input className='form-input' {...otherProps} />
    {label && (<label className={`${otherProps.value.length ? 'shrink' : ''} form-input-label`}>{label}</label>)}
  </div>
);

6Nel tuo codice: FormInput e Button

const FormInput = ({ label, ...otherProps }) => {
  return (
    <div className='group'>
      <input className='form-input' {...otherProps} />
      {label && (
        <label
          className={`${
            otherProps.value.length ? 'shrink' : ''
          } form-input-label`}
        >
          {label}
        </label>
      )}
    </div>
  );
};

const BUTTON_TYPE_CLASSES = {
  google: 'google-sign-in',
  inverted: 'inverted',
};

const Button = ({ children, buttonType, ...otherProps }) => {
  return (
    <button
      className={`button-container ${BUTTON_TYPE_CLASSES[buttonType]}`}
      {...otherProps}
    >
      {children}
    </button>
  );
};
  1. Rest: label serve al componente, tutto il resto è per l'<input>.
  2. Spread delle props: value, onChange, name, type, required arrivano all'input DOM. FormInput è "trasparente".
  3. Render condizionale: {label && …} mostra la label solo se c'è.
  4. Attenzione: otherProps.value.length presuppone che value esista. Un FormInput senza value va in crash: Cannot read properties of undefined (reading 'length').
  5. La label "shrink": se c'è testo, la label si rimpicciolisce e sale. È uno stile derivato dallo state, senza state aggiuntivo.
  6. Mappa tipo → classe: un oggetto al posto di un if/else.
  7. Il dettaglio da dev: senza buttonType, BUTTON_TYPE_CLASSES[undefined] vale undefined, quindi la classe diventa "button-container undefined". Non rompe niente, ma nel DOM finisce una classe chiamata "undefined".
  8. children: il testo tra <Button> e </Button>.

"I dati scendono, gli eventi salgono" I valori scendono come props (SignUpForm → FormInput → DOM). I cambiamenti risalgono come chiamate di funzione (DOM → onChange → handleChange del genitore). FormInput non possiede niente: è un componente "di presentazione". È la stessa direzione dei dati di Context (M5), solo su distanze più corte.

8Documentazione ufficiale ↔ corso

DOC react.dev › <input> › Controlling an input with a state variable

function Form() {
  const [firstName, setFirstName] = useState(''); // Declare a state variable...
  // ...
  return (
    <input
      value={firstName} // ...force the input's value to match the state variable...
      onChange={e => setFirstName(e.target.value)} // ... and update the state variable on any edits!
    />
  );
}

CORSO (generalizzato a N campi)

const [formFields, setFormFields] = useState(defaultFormFields);

const handleChange = (event) => {
  const { name, value } = event.target;
  setFormFields({ ...formFields, [name]: value });
};

<FormInput name='email' value={email} onChange={handleChange} />
<FormInput name='password' value={password} onChange={handleChange} />

Tabella di traduzione: uno state per campo (doc) → uno state a oggetto (corso); un handler inline per campo → un handler unico che usa name; setFirstName(e.target.value) → { ...formFields, [name]: value }.

Troubleshooting della doc: due errori che vedrai

  • value senza onChange: la doc spiega che, se passi value senza onChange, è impossibile scrivere nell'input, e in console compare un avviso su un campo che diventerebbe "read-only".
  • "A component is changing an uncontrolled input to be controlled": la doc dice che un input controllato deve ricevere sempre una stringa, mai null o undefined, e suggerisce value={someValue ?? ''}. Succede, per esempio, se il default dello state non ha tutte le chiavi.

9Errori tipici

❶ name diverso dalla chiave dello state

<FormInput name='mail' value={email} onChange={handleChange} />

Passo per passo: scrivi "a" → name = 'mail' → { ...formFields, mail: 'a' } → email resta '' → l'input mostra '' → sembra che la tastiera non funzioni. Intanto lo state si riempie di una chiave mail che nessuno legge.

Modello sbagliato"L'input è collegato al suo value."
Modello giusto"L'input legge da value e scrive tramite name. Devono indicare la stessa chiave."

❷ Modificare lo state sul posto

formFields[name] = value;
setFormFields(formFields);   // stesso riferimento → nessun re-render

❸ Aggiornamenti rapidi con lo state "vecchio"

setFormFields({ ...formFields, email: 'a' });
setFormFields({ ...formFields, password: 'b' });   // sovrascrive: email torna vecchia!

Entrambe le chiamate partono dalla stessa fotografia (M0). La seconda non vede la prima. Soluzione: la forma funzionale, setFormFields((prev) => ({ ...prev, [name]: value })).

❹ onClick sul bottone invece di onSubmit sul form

Con onClick sul bottone perdi l'invio con il tasto Invio e la validazione nativa (required, type="email"). Il submit è un evento del form.

❺ Il bottone Google che invia il form

Dentro un <form>, un <button> senza type è type="submit" di default. Per questo il tuo bottone Google ha type='button': senza, il click partirebbe anche come submit del login con email.
