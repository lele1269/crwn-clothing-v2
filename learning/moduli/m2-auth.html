1Il problema: l'identità è difficile da fare bene

Un sistema di login fatto in casa richiede: salvare le password in modo sicuro (hash con salt, mai in chiaro), proteggersi dai tentativi a raffica, gestire le sessioni, il reset password, la verifica email, OAuth con Google… Ogni errore è una falla di sicurezza. Firebase Auth fa tutto questo per te e ti restituisce un'informazione semplice: chi è questo utente (uid), garantito dal server.

2Teoria e terminologia

I codici di errore e la "email enumeration protection"

Gli errori di Auth sono FirebaseError con una proprietà code, per esempio 'auth/email-already-in-use'. Attenzione: per i progetti Firebase creati dal 15 settembre 2023 in poi, la email enumeration protection è attiva di default. Con questa protezione, un login fallito (email inesistente oppure password sbagliata) restituisce lo stesso errore, INVALID_LOGIN_CREDENTIALS, che l'SDK JavaScript traduce in auth/invalid-credential. Così un malintenzionato non può scoprire quali email sono registrate.

CodiceQuando
auth/email-already-in-usesign-up con un'email già registrata
auth/weak-passwordpassword troppo corta (meno di 6 caratteri)
auth/invalid-emailemail malformata
auth/invalid-credentiallogin fallito, con la protezione attiva
auth/wrong-password, auth/user-not-foundlogin fallito, ma solo con la protezione disattivata (progetti vecchi)
auth/popup-closed-by-userl'utente ha chiuso il popup di Google
auth/too-many-requeststroppi tentativi: blocco temporaneo

3Modello mentale: la reception dell'hotel

🏨
Auth è la reception. Mostri un documento (il provider): la carta d'identità (email e password) o una lettera di presentazione di Google (OAuth). La reception verifica e ti dà una tessera magnetica (l'ID token) con scadenza: a ogni porta (Firestore) la tessera viene letta e le Rules decidono se aprire. Sulla tessera c'è il tuo numero di cliente (uid), che resta lo stesso per sempre. Il portiere di notte (persistenza) si ricorda di te se torni: non devi rifare il check-in.

4Flusso animato

// firebase.utils.js
export const signInWithGooglePopup = () =>
  signInWithPopup(auth, googleProvider);

export const signInAuthUserWithEmailAndPassword = async (email, password) => {
  if (!email || !password) return;
  return await signInWithEmailAndPassword(auth, email, password);
};

// sign-in-form.component.jsx
const signInWithGoogle = async () => {
  const { user } = await signInWithGooglePopup();
  await createUserDocumentFromAuth(user);
};

const handleSubmit = async (event) => {
  event.preventDefault();
  try {
    const response = await signInAuthUserWithEmailAndPassword(email, password);
    resetFormFields();
  } catch (error) {
    switch (error.code) {
      case 'auth/wrong-password': alert('incorrect password for email'); break;
      case 'auth/user-not-found': alert('no user associated with this email'); break;
      default: console.log(error);
    }
  }
};

5Forma dei dati

UserCredential (Google)
L'errore di un login fallito
Non salvare l'oggetto User intero User contiene metodi, token e riferimenti interni. Nel documento Firestore salvi solo i campi che ti servono (displayName, email), come fa createUserDocumentFromAuth. Nello state di React invece l'oggetto intero va bene: lo legge solo la tua app.

6Nel tuo codice

const googleProvider = new GoogleAuthProvider();

googleProvider.setCustomParameters({
  prompt: 'select_account',
});

export const auth = getAuth();
export const signInWithGooglePopup = () =>
  signInWithPopup(auth, googleProvider);
export const signInWithGoogleRedirect = () =>
  signInWithRedirect(auth, googleProvider);

export const createAuthUserWithEmailAndPassword = async (email, password) => {
  if (!email || !password) return;
  return await createUserWithEmailAndPassword(auth, email, password);
};

export const signInAuthUserWithEmailAndPassword = async (email, password) => {
  if (!email || !password) return;
  return await signInWithEmailAndPassword(auth, email, password);
};
  1. Provider configurato una volta. prompt: 'select_account' obbliga Google a mostrare la scelta dell'account anche se ne hai uno solo già collegato.
  2. auth: l'istanza condivisa da tutte le funzioni sotto.
  3. Wrapper sottili: nascondono auth e il provider ai componenti. Restituisce direttamente la Promise di signInWithPopup.
  4. Redirect: esportata ma non usata nei tuoi componenti. Se la usassi, ti servirebbe anche getRedirectResult al ritorno (oppure il listener di M5, che se ne accorge da solo).
  5. Guardia: senza email o password restituisce undefined. Attenzione: chi chiama e fa const { user } = await … va in crash (Cannot destructure property 'user' of undefined). È una guardia che sposta il problema invece di risolverlo.
  6. return await: dentro un try/catch servirebbe (M0, domanda 7). Qui non c'è try, quindi return da solo sarebbe equivalente.

Lo snippet usa .then, il corso async/await

const auth = getAuth();
createUserWithEmailAndPassword(auth, email, password)
  .then((userCredential) => {
    // Signed up
    const user = userCredential.user;
    // ...

  .catch((error) => {
    const errorCode = error.code;
    const errorMessage = error.message;

export const createAuthUserWithEmailAndPassword = async (email, password) => {
  if (!email || !password) return;
  return await createUserWithEmailAndPassword(auth, email, password);
};

try {
  const { user } = await createAuthUserWithEmailAndPassword(email, password);
  // ...
} catch (error) {
  if (error.code === 'auth/email-already-in-use') { /* ... */ }
}

Snippet di Firebase (Google), licenza Apache 2.0. Traduzione .then → await: vedi M0 ⑧.

Cosa dice la reference (e il corso no)

  • createUserWithEmailAndPassword: "On successful creation of the user account, this user will also be signed in to your application." Quindi il listener di M5 scatta già durante il sign-up: è l'origine della race condition di M5, domanda 7.
  • signInWithPopup: "This method does not work in a Node.js environment". Per questo negli esercizi usiamo un simulatore.
  • signOut: restituisce Promise<void>, come setDoc.
  • onAuthStateChanged: i parametri error e completed sono deprecati e non vengono mai chiamati.
Il bug che trovi solo leggendo la documentazione La pagina Google Cloud sulla email enumeration protection dice che i progetti creati dal 15 settembre 2023 la hanno attiva di default, e che i login falliti restituiscono INVALID_LOGIN_CREDENTIALS. Nel pacchetto firebase che hai installato questo errore viene tradotto in "invalid-credential" (l'ho verificato nel codice dell'SDK in node_modules). Il tuo progetto è recente, quindi gli case 'auth/wrong-password' e 'auth/user-not-found' del tuo SignInForm non scatteranno mai: l'utente che sbaglia password non vede nessun messaggio, solo un log in console.

Il corso è stato registrato prima di questo cambiamento. La documentazione è più aggiornata del video.

9Errori tipici

❶ Fidarsi dei codici di errore visti nel video

Modello sbagliato"Se il corso controlla quel codice, quel codice arriva."
Modello giusto"I codici dipendono dalla configurazione del progetto e dalla versione dell'SDK. Li verifico: provo il caso (password sbagliata) e guardo error.code in console."

❷ "Con email e password ho il displayName"

createUserWithEmailAndPassword riceve solo email e password: user.displayName è null. Il nome del form va salvato a parte (in Firestore con additionalInformation, oppure nel profilo Auth con updateProfile(user, { displayName })).

❸ Ogni errore in un alert

auth/popup-closed-by-user non è un errore dell'utente: è una scelta. Mostrarlo come un errore è cattiva UX. Gli errori si dividono in tre gruppi: da mostrare (credenziali sbagliate), da ignorare (popup chiuso), da loggare e mostrare in forma generica (rete, errori interni).

❹ Usare auth.currentUser all'avvio

Al caricamento della pagina, la sessione viene ripristinata in modo asincrono: auth.currentUser può valere null per qualche istante anche se l'utente è loggato. Per sapere "chi è loggato" si usa l'observer (M5).
