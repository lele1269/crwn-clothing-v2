1Perché la documentazione sembra un muro

Non è una tua mancanza: la documentazione è scritta in un modo diverso da un corso, per un motivo preciso.

Un corso…La documentazione…Conseguenza per te
segue un progetto (CRWN)deve servire tutti i progettigli esempi sono generici (cities, "SF"): devi tradurli tu
avvolge le chiamate in funzioni (createUserDocumentFromAuth)mostra le chiamate "nude"non ritrovi i nomi del corso: devi riconoscere i mattoni dentro le funzioni
va in un ordineè un archivio da consultare, non da leggere dall'iniziodevi sapere cosa cerchi prima di aprirla
sceglie per te piattaforma e versionecopre Web, iOS, Android, Node, versioni vecchie e nuovedevi scegliere la scheda giusta
spiega solo ciò che serveè completa: tutte le opzioni, tutti i casi limitedevi imparare a ignorare quello che non ti serve adesso
Il cambio di prospettiva La documentazione non si legge, si interroga. Ci arrivi con una domanda precisa ("come leggo un documento?") e ne esci con una risposta precisa. Se la apri senza una domanda, ti perdi.

2I 4 tipi di pagina

Quasi tutte le documentazioni moderne hanno quattro tipi di pagina, ognuno con uno scopo diverso. Riconoscere il tipo è il primo passo: ti dice come leggere la pagina.

L'errore più comune Usare la reference come se fosse un tutorial (leggerla dall'inizio, perdersi alla terza riga) oppure fermarsi al tutorial e non aprire mai la reference. Il dev esperto parte dalla guida per avere lo snippet, poi apre la reference sulla funzione che sta usando per verificare i dettagli.

Prendiamo la pagina Get data with Cloud Firestore. Le sue sezioni sono queste (titoli reali della pagina):

Come la leggi:

  • Salta "Before you begin" e "Initialize": lo hai già fatto in firebase.utils.js. Torna a leggerle solo se qualcosa non parte.
  • "Example data" è importante: crea i dati (cities, SF…) usati in tutti gli snippet. Guardala per capire di cosa parlano gli esempi.
  • Vai dritto alla sezione che risponde alla tua domanda.
  • Le schede delle lingue: ci sono due schede chiamate "Web". La prima è l'API modulare (doc(db, …), la tua). La seconda è l'API namespaced, quella vecchia (db.collection(…).doc(…)). Le riconosci dal codice, non dal nome.
✔ Modulare: la tua
import { doc, getDoc } from "firebase/firestore";
const snap = await getDoc(doc(db, "cities", "SF"));
Funzioni importate e chiamate passando db.
✘ Namespaced: non mescolarla
const snap = await db.collection("cities").doc("SF").get();
Metodi a catena su db. È quella dei tutorial vecchi (v8).

4Leggere una firma della API reference

La reference di Firebase è scritta in TypeScript: JavaScript con i tipi scritti esplicitamente. Non devi saper scrivere TypeScript per leggerla. Ti bastano 6 simboli.

getDoc: la firma ufficiale

Passa il mouse sui punti della lista per evidenziare le parti della firma.

export declare function getDoc<
  AppModelType,
  DbModelType extends DocumentData
>(
  reference: DocumentReference<AppModelType, DbModelType>
): Promise<DocumentSnapshot<AppModelType, DbModelType>>;
  1. export declare function getDoc: "esiste una funzione esportata che si chiama getDoc". declare vuol dire che qui c'è solo la descrizione, non il codice. Puoi importarla.
  2. <AppModelType, DbModelType …>: i generics, tipi "segnaposto" per chi usa TypeScript con modelli personalizzati. In JavaScript puoi ignorarli. Mentalmente leggi DocumentReference<…> come semplice DocumentReference.
  3. reference: DocumentReference: un parametro. Prima dei : c'è il nome, dopo il tipo. Vuol dire: "dammi un indirizzo", cioè quello che produce doc().
  4. ): Promise<DocumentSnapshot>: i : dopo la parentesi chiusa indicano cosa restituisce. Una Promise di una foto. Quindi ti serve await e quello che ottieni è uno snapshot.
La firma tradotta in una frase getDoc riceve un indirizzo e restituisce la promessa di una fotografia. Ogni firma si può ridurre a una frase così: "[nome] riceve [parametri] e restituisce [tipo di ritorno]". Se riesci a dirla, hai capito la funzione.

doc: parametri "a fisarmonica" ed eccezioni

export declare function doc(
  firestore: Firestore,
  path: string,
  ...pathSegments: string[]
): DocumentReference<DocumentData, DocumentData>;

// Exceptions:
// If the final path has an odd number of segments
// and does not point to a document.
  1. firestore: Firestore: l'istanza db.
  2. path: string: almeno una stringa, il percorso (anche con gli slash: 'users/abc').
  3. ...pathSegments: string[]: il rest parameter. I tre puntini vogliono dire "altre stringhe, quante vuoi, separate da virgole". Per questo doc(db, 'users', uid) e doc(db, 'users/' + uid) sono equivalenti. string[] = array di stringhe.
  4. Ritorno: un DocumentReference, senza Promise. Quindi è sincrona, niente await.
  5. Exceptions: la sezione che quasi tutti saltano. Ti dice che con un numero dispari di segmenti lancia un errore, subito e in modo sincrono.

setDoc: due firme, una funzione (overload)

// setDoc(reference, data)
export declare function setDoc(reference: DocumentReference, data: WithFieldValue): Promise<void>;

// setDoc(reference, data, options)
export declare function setDoc(reference: DocumentReference, data: PartialWithFieldValue, options: SetOptions): Promise<void>;

Generics rimossi per leggibilità. Firma completa: API reference di setDoc.

Quando una funzione ha più firme (overload), la reference le elenca separatamente. Leggile come "puoi chiamarla in uno di questi modi". Dettagli che ora sai leggere:

  • Promise<void>: è una Promise, ma il valore finale è niente. Il await serve ad aspettare (o a intercettare l'errore), non a ottenere un dato. const x = await setDoc(...) → x è undefined.
  • WithFieldValue e PartialWithFieldValue: con le opzioni (per esempio {merge: true}) puoi passare dati parziali. Senza opzioni, i dati sono il documento intero.

5Leggere MDN (la reference di JavaScript)

MDN Web Docs è la documentazione di riferimento di JavaScript e delle API del browser. Ogni pagina di un metodo ha sempre le stesse sezioni, nello stesso ordine:

Array.prototype.find()
  1. Intro + Try it: una frase e un esempio interattivo
  2. Syntax: come si chiama
  3. Parameters: cosa passi
  4. Return value: cosa ottieni
  5. Exceptions (non sempre): quando esplode
  6. Description: come funziona davvero
  7. Examples: casi d'uso
  8. Specifications · Browser compatibility

Ordine di lettura del dev: Syntax → Return value → Parameters → un esempio. Description solo se qualcosa ti sorprende. Exceptions sempre, almeno con un'occhiata.

La sintassi su più righe indica gli argomenti opzionali:

find(callbackFn)
find(callbackFn, thisArg)

Due righe vuol dire che thisArg è facoltativo. Nella sezione Parameters, callbackFn è descritta con i suoi argomenti: element, index, array.

"prototype" e metodi statici: il dettaglio che confonde

Titolo su MDNTipoCome lo scrivi
Array.prototype.find()metodo d'istanza: lo chiami su un arrayproducts.find(p => p.id === 3)
String.prototype.trim()metodo d'istanza su una stringadisplayName.trim()
Object.entries()metodo statico: lo chiami sul costruttoreObject.entries(formFields)
Array.isArray()metodo staticoArray.isArray(x)
Regola Se nel titolo c'è .prototype., al posto di Array.prototype metti il tuo array. Se non c'è, scrivi il nome esattamente com'è. formFields.entries() non esiste: entries è un metodo statico di Object.

6Il metodo in 6 passi

Esempio svolto: "voglio contare quante volte un utente ha fatto login"

  1. Domanda: "incrementare un numero in un documento".
  2. Tipo di pagina: è un "come si fa", quindi una guida. Su Firebase: Add data → sezione Increment a numeric value.
  3. Versione: scheda Web modulare, si riconosce dall'import da "firebase/firestore".
  4. Snippet: 
    import { doc, updateDoc, increment } from "firebase/firestore";

const washingtonRef = doc(db, "cities", "DC");

await updateDoc(washingtonRef, {
    population: increment(50)
});
    Riga per riga: indirizzo (doc), poi aggiornamento di un solo campo (updateDoc), con un valore speciale (increment) che chiede al server di sommare.
  5. Traduci: "cities" → 'users', "DC" → uid (parametro), population → loginCount, 50 → 1.
  6. Verifica nella reference:
    • updateDoc: "The update will fail if applied to a document that does not exist." → se l'utente non ha documento, errore. Devo gestirlo?
    • increment: se il campo non esiste ancora, la trasformazione lo imposta al valore dato. Al primo login loginCount diventa 1 senza bisogno di inizializzarlo.

Ecco la differenza tra copiare uno snippet e capirlo: i due dettagli del passo 6 non sono nello snippet, sono nella reference.

7Il ciclo mentale del dev

Leggere la documentazione è un caso particolare di un'abitudine più generale. Chi diventa bravo non è chi sbaglia meno: è chi impara di più da ogni errore. Lo fa con un ciclo preciso, che vale per il codice, per la doc e per questi esercizi.

Studente passivo
  • Esegue il codice per "vedere cosa fa".
  • Se funziona va avanti, anche senza sapere perché.
  • Se non funziona cambia righe a caso finché va.
  • Legge l'errore a metà, o non lo legge.
  • Impara la riga, non l'idea.
Dev
  • Prima di eseguire, scrive cosa si aspetta.
  • Quando funziona, sa dire perché e cosa lo romperebbe.
  • Quando non funziona, riduce il problema al caso più piccolo.
  • Legge l'errore tutto: tipo, messaggio, file, riga.
  • Per ogni funzione si chiede: qual è il contratto? Cosa entra, cosa esce, quando fallisce.
Le 5 domande da farsi sempre
  1. Cosa entra e cosa esce, con valori concreti?
  2. È sincrono o asincrono? Dove aspetto?
  3. Cosa succede se il dato manca (null, undefined, array vuoto)?
  4. Chi intercetta gli errori, e chi ne viene a sapere?
  5. Questo è un indirizzo o un valore? Un riferimento o una copia?

8Errori tipici nel leggere la documentazione

❶ Copiare codice della versione sbagliata

Un tutorial del 2020 o un vecchio post di Stack Overflow ti danno firebase.firestore().collection('users'). Lo incolli, e firebase is not defined.

Modello sbagliato"Se è codice Firebase, funziona con Firebase."
Modello giusto"Prima di copiare, controllo la versione: import modulari da 'firebase/…' sì, catene su firebase. o db. no."

❷ Ignorare "Returns"

Non leggi che getDoc restituisce una Promise, dimentichi await e ottieni snap.exists is not a function.

Modello sbagliato"Una funzione mi dà quello che ha nel nome."
Modello giusto"Una funzione mi dà quello che c'è scritto dopo i due punti della firma. Se c'è Promise, serve await."

❸ Copiare i nomi dell'esempio

Nel tuo codice compare doc(db, "cities", uid): hai copiato lo snippet ma non l'hai tradotto. Il codice non dà errore, scrive nella collection sbagliata.

Modello sbagliato"Lo snippet è codice da incollare."
Modello giusto"Lo snippet è uno stampo: ogni nome va tradotto nel mio dominio."

❹ Leggere lo snippet e saltare le note

La nota sull'await di setDoc, l'avvertimento che deleteDoc non cancella le sotto-collection, il fatto che updateDoc fallisce sui documenti inesistenti: tutte queste informazioni stanno nelle note e nella reference, non negli snippet.

❺ Confondere statico e d'istanza

formFields.entries()        // TypeError: formFields.entries is not a function
Object.entries(formFields)  // [['displayName', 'Leo'], ['email', '…'], …]
