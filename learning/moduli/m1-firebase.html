1Il problema: un negozio ha bisogno di un backend

CRWN deve registrare utenti, verificarne la password, salvare profili e carrelli. Tradizionalmente servirebbero un server (Node, Java…), un database, un sistema di login sicuro (hashing delle password, sessioni, reset), un hosting e la manutenzione di tutto questo. Firebase è un BaaS: noleggi questi pezzi già pronti, e il tuo frontend ci parla direttamente.

Cosa guadagniNiente server da scrivere né da tenere acceso. Login sicuro pronto. Un database che scala. Un piano gratuito per imparare.
Cosa cambiaIl "server" non lo controlli tu: le regole di accesso le scrivi come Security Rules. E sei legato all'API di Google (lock-in): è un motivo in più per isolare Firebase in firebase.utils.js.

La domanda chiave: se l'apiKey è pubblica, cosa protegge i dati? Tre cose, tutte lato server: le Security Rules (chi può leggere e scrivere cosa), l'autenticazione (request.auth nelle regole sa chi sei) e, se vuoi, App Check (verifica che la richiesta arrivi dalla tua app). Il codice del frontend non protegge niente: chiunque può aprire i DevTools e chiamare l'SDK a mano.

3Modello mentale: il centralino

☎️
Il progetto Firebase è un'azienda con diversi uffici (Auth, Firestore, Storage). La config è il numero di telefono dell'azienda: tutti possono conoscerlo. initializeApp è salvare il numero in rubrica. getAuth() e getFirestore() sono gli interni degli uffici. Le Security Rules sono il centralinista: per ogni chiamata decide se passartela, in base a chi sei (request.auth) e a cosa chiedi.

import { initializeApp } from 'firebase/app';

  getAuth,
  signInWithPopup,
  GoogleAuthProvider,
} from 'firebase/auth';

const firebaseConfig = {
  apiKey: "AIza…",
  authDomain: "crwn-clothing-db-ad3ed.firebaseapp.com",
  projectId: "crwn-clothing-db-ad3ed",
  // …
};

const firebaseApp = initializeApp(firebaseConfig);

const googleProvider = new GoogleAuthProvider();
googleProvider.setCustomParameters({ prompt: 'select_account' });

export const auth = getAuth();
export const db = getFirestore();
  1. Tre sotto-pacchetti: app (il nucleo), auth, firestore. Ognuno porta nel bundle solo ciò che importi.
  2. Config: dati di identificazione, non segreti. Ma non metterci mai chiavi di servizio (per esempio un service account): quelle sì che danno accesso totale.
  3. initializeApp: firebaseApp non viene più usata esplicitamente. getAuth() e getFirestore() senza argomenti trovano da sole l'app '[DEFAULT]'.
  4. Provider Google: un oggetto di configurazione per il login con Google, creato una volta sola.
  5. Istanze esportate: tutti i moduli che importano auth o db ricevono le stesse istanze.
Perché il codice in cima a un modulo viene eseguito una volta sola Un modulo ES viene valutato una volta, al primo import. Gli import successivi, da qualsiasi file, ricevono gli stessi export già calcolati: il modulo resta in cache. Per questo initializeApp non viene ripetuta anche se dieci componenti importano firebase.utils.js. È un singleton "gratuito".

DifferenzaSpiegazione
'firebase/firestore/lite' contro 'firebase/firestore'Leggi l'import! La versione lite è più leggera e lavora solo con richieste REST: niente listener in tempo reale e niente cache offline. Il corso usa la versione completa. Se copi lo snippet così com'è, cambi libreria senza accorgertene.
getFirestore(app) contro getFirestore()Due overload (T1, esercizio E1): senza argomento si usa l'app di default.
const app contro const firebaseAppSolo un nome. Nel corso la variabile non viene più usata, ma initializeApp va chiamata comunque: è lei che registra l'app di default.
// import { } from 'firebase/<service>'Il commento è una regola: ogni servizio ha il suo sotto-percorso.

9Errori tipici

❶ Usare un servizio prima di initializeApp

FirebaseError: Firebase: No Firebase App '[DEFAULT]' has been created - call initializeApp() first (app/no-app).

Succede se un modulo chiama getAuth() prima che initializeApp sia stata eseguita, per esempio perché hai spostato le chiamate in un altro file e l'ordine degli import è cambiato. Il messaggio dice esattamente cosa fare.

❷ Inizializzare due volte con config diverse

FirebaseError: Firebase: Firebase App named '[DEFAULT]' already exists with different options.
Existing: '…'. New: '…'. (app/duplicate-app).

Con la stessa config, le versioni recenti dell'SDK restituiscono l'app esistente. Con config diverse e lo stesso nome, errore. Se ti servono due progetti, usa due nomi: initializeApp(config2, 'secondo').

❸ "Nascondo l'apiKey in .env, così è sicuro"

In Create React App le variabili REACT_APP_* vengono scritte nel bundle in fase di build: finiscono comunque nel browser. Un .env serve a gestire ambienti diversi (sviluppo, produzione) o a non pubblicare la config su GitHub per ordine, non a renderla segreta.

Modello sbagliato"Se il segreto non si vede nel codice sorgente, è al sicuro."
Modello giusto"Tutto ciò che il browser riceve è pubblico. La sicurezza sta sul server: Rules, Auth, App Check."

❹ Mischiare API compat e modulare

import firebase from 'firebase/compat/app';   // vecchio stile
import { getAuth } from 'firebase/auth';       // nuovo stile

Funziona, ma raddoppia il codice nel bundle e confonde chi legge. In un progetto nuovo si usa solo la modulare.
