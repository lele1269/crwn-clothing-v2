1Il problema: Auth sa CHI sei, non COSA sei

Quando un utente fa login, Firebase Authentication ti restituisce un oggetto user con un uid, l'email e poco altro. Auth è un sistema di identità: verifica che tu sia tu. Non è fatto per conservare il nome che hai scelto in fase di registrazione, la data di iscrizione, gli indirizzi di spedizione o lo storico degli ordini.

Per quello serve un database. In CRWN il database è Firestore, e il collegamento tra i due mondi è uno solo: l'uid.

L'idea da portarsi a casa Sono due servizi diversi, su server diversi, con dati diversi. Firestore non sa niente del login: sei tu, nel codice, a creare un documento il cui ID è uguale all'uid di Auth. Se non lo fai, l'utente esiste in Auth ma per il tuo database è un fantasma. È proprio quello che fa createUserDocumentFromAuth.

2Teoria e terminologia

Che tipo di database è Firestore

Firestore è un database NoSQL documentale gestito da Google: non installi niente e non scrivi un server. Il tuo frontend ci parla direttamente attraverso l'SDK (il pacchetto firebase). Se hai visto i database SQL, il confronto aiuta:

SQL (tabelle)Firestore (documenti)In CRWN
TabellaCollectionusers
RigaDocumentousers/g7Hk2
Colonna (uguale per tutte le righe)Campo (ogni documento può avere i suoi)displayName, email, createdAt
Chiave primariaID del documentol'uid di Auth
JOIN tra tabelleNon esiste: si legge più volte o si duplicano i dati—

La regola d'oro dei percorsi

Ogni dato ha un percorso che alterna sempre collection e documento. Una collection contiene solo documenti, e un documento contiene campi e, se serve, sotto-collection.

users                         // 1 segmento  → dispari → COLLECTION
users/g7Hk2                   // 2 segmenti  → pari    → DOCUMENTO
users/g7Hk2/orders            // 3 segmenti  → dispari → COLLECTION
users/g7Hk2/orders/o-001      // 4 segmenti  → pari    → DOCUMENTO
users/g7Hk2/displayName       // ✘ SBAGLIATO: un campo non è un segmento del percorso!

Le quattro funzioni che usi (SDK modulare)

FunzioneCosa riceveCosa restituisceVa in rete?
getFirestore()(l'app Firebase inizializzata)db: l'istanza del databaseNo

Più avanti incontrerai anche updateDoc (modifica solo alcuni campi), collection(), getDocs() e writeBatch(). La logica resta la stessa: prima costruisci un indirizzo, poi fai un'operazione su quell'indirizzo.

Perché "modulare"? Nell'SDK v9 e successivi (tu hai il pacchetto firebase 13.x) non si scrive più db.collection('users').doc(uid).get() a catena, come nei vecchi tutorial. Si importano funzioni singole: doc(db, …), getDoc(ref). Il motivo è il tree-shaking: il bundler include nel bundle solo le funzioni che importi davvero, quindi l'app è più leggera. Se trovi online codice "a catena", è della vecchia API.

Tipi di dato e una trappola

Un campo può contenere stringhe, numeri, booleani, null, array, mappe (oggetti annidati), riferimenti ad altri documenti e Timestamp. La trappola sono le date: quello che scrivi non è quello che rileggi.

Scrivi
setDoc(ref, { createdAt: new Date() })
un oggetto Date di JavaScript
Rileggi
snap.data().createdAt         // Timestamp {seconds, nanoseconds}
snap.data().createdAt.toDate() // Date
un Timestamp di Firestore

Altro dettaglio: undefined non è un valore ammesso. Se un campo vale undefined, setDoc lancia un errore. null invece è accettato.

Sicurezza: chi protegge davvero il database

Nel tuo firebase.utils.js c'è un apiKey in chiaro. È normale: per Firebase l'apiKey identifica il progetto, non dà permessi. Chiunque apra i DevTools sul tuo sito la vede comunque. Cosa impedisce allora a un estraneo di leggere i documenti di tutti gli utenti? Le Security Rules, che vengono valutate sul server a ogni richiesta:

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      // ognuno legge e scrive SOLO il proprio documento
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
  }
}
Controlla le tue regole Nei corsi si crea spesso il database in "test mode", cioè con tutto aperto a tutti fino a una data di scadenza. Quando scade, ogni lettura e scrittura fallisce con permission-denied e sembra che "il codice si sia rotto da solo". Vai in Console Firebase → Firestore → Regole e guarda cosa c'è scritto.

3Modello mentale: l'archivio

🗄️
Firestore è un grande archivio. Il db è l'archivio intero. Una collection è un cassetto con un'etichetta (users). Un documento è una cartella nel cassetto, con un'etichetta sua (l'ID, g7Hk2). I campi sono i fogli dentro la cartella. Una sotto-collection è un piccolo cassetto attaccato alla cartella.

L'etichetta della cartella (l'ID) non è uno dei fogli: per questo data() non contiene l'id.

Indirizzo e fotografia: la distinzione più importante del modulo

Come ragionarci Davanti a una variabile Firestore chiediti sempre: "questa è un indirizzo o una fotografia?". Su un indirizzo puoi fare operazioni (leggere, scrivere). Da una fotografia puoi guardare i dati di un istante passato. Metà dei bug con Firestore nascono dal confondere le due cose.

4Flusso animato: createUserDocumentFromAuth

Usa Avanti ▶ (o le frecce della tastiera dopo aver cliccato il riquadro). Ogni passo mostra cosa si accende, la riga di codice in esecuzione e il contenuto delle variabili. Prova entrambe le varianti: il confronto è il punto della lezione.

export const createUserDocumentFromAuth = async (
  userAuth,
  additionalInformation = {}
) => {
  if (!userAuth) return;

  const userDocRef = doc(db, 'users', userAuth.uid);

  const userSnapshot = await getDoc(userDocRef);

  if (!userSnapshot.exists()) {
    const { displayName, email } = userAuth;
    const createdAt = new Date();

    try {
      await setDoc(userDocRef, {
        displayName,
        email,
        createdAt,
        ...additionalInformation,
      });
    } catch (error) {
      console.log('error creating the user', error.message);
    }
  }

  return userDocRef;
};
Cosa devi aver notato confrontando le due varianti La funzione è idempotente: puoi chiamarla a ogni login senza paura. Il primo accesso fa 1 lettura + 1 scrittura, tutti i successivi fanno 1 lettura + 0 scritture. È la lettura (la "foto") che decide se scrivere. Senza quella foto, ogni login sovrascriverebbe il profilo.

5Forma dei dati: gli oggetti veri

Ecco gli oggetti come li vedresti con un console.log, semplificati ai campi che contano. Apri e chiudi i nodi come nei DevTools.

AUTH userAuth (cioè response.user)
FIRESTORE userDocRef (dopo doc())
FIRESTORE userSnapshot · documento esistente
FIRESTORE userSnapshot · documento inesistente
Nota che exists e data sono metodi (ƒ), non proprietà. snap.exists senza parentesi è una funzione, e una funzione in un if vale sempre true. Il codice non dà errore: semplicemente sbaglia ogni volta.

6Nel tuo codice: firebase.utils.js

Passa il mouse (o tocca) su ogni punto della lista per evidenziare le righe corrispondenti.

import { initializeApp } from 'firebase/app';
import { getFirestore, doc, getDoc, setDoc } from 'firebase/firestore';

const firebaseApp = initializeApp(firebaseConfig);

export const db = getFirestore();

export const createUserDocumentFromAuth = async (
  userAuth,
  additionalInformation = {}
) => {
  if (!userAuth) return;
  const userDocRef = doc(db, 'users', userAuth.uid);
  const userSnapshot = await getDoc(userDocRef);

  if (!userSnapshot.exists()) {
    const { displayName, email } = userAuth;
    const createdAt = new Date();
    try {
      await setDoc(userDocRef, {
        displayName,
        email,
        createdAt,
        ...additionalInformation,
      });
    } catch (error) {
      console.log('error creating the user', error.message);
    }
  }
  return userDocRef;
};
  1. Import modulari. Importi solo 4 funzioni: è quello che rende possibile il tree-shaking.
  2. Ordine obbligato. Prima initializeApp, poi getFirestore(). Senza argomenti, getFirestore usa l'app di default appena inizializzata. db viene creato una volta e condiviso da tutta l'app (singleton).
  3. Parametro di default. additionalInformation = {} significa che se non passi niente vale un oggetto vuoto, così lo spread alla riga 24 non esplode mai.
  4. Guardia. Esce subito se non c'è un utente. Restituisce undefined.
  5. Indirizzo. uid come ID del documento: è il ponte con Auth. Non c'è nessuna chiamata di rete.
  6. Foto. L'unica lettura di rete. await sospende la funzione finché non arriva la risposta.
  7. Decisione. Notare il !: entra nell'if solo se il documento non esiste.
  8. Destructuring e data. Estrae due campi da userAuth. new Date() diventerà un Timestamp sul server.
  9. Ordine dello spread. ...additionalInformation viene dopo, quindi vince. È così che il displayName del form di sign-up sostituisce il null di Auth.
  10. try/catch con await. L'errore della scrittura viene intercettato solo perché c'è await. Senza, la Promise fallirebbe "altrove" e il catch non la vedrebbe mai.
  11. Ritorno. Restituisce l'indirizzo, riutilizzabile da chi chiama.

7Nei componenti: come viaggiano i dati nella tua app

Finora abbiamo guardato una funzione isolata. Nella tua app però i dati partono da un componente React, passano per firebase.utils.js, entrano nell'SDK, arrivano ai server e poi tornano indietro. Per capire davvero devi vedere tutti i livelli insieme.

I quattro livelli (e chi importa cosa)

ChiConosceNON conosce
SignUpFormlo state formFields, il form, i messaggi di errore per l'utenteauth, db, doc(), il percorso users/…
firebase.utils.jsauth, db, il provider Google, la struttura users/{uid}che esiste un form, cos'è formFields, cosa mostra la UI
SDK firebase/*come parlare con i server Googleche la tua app si chiama CRWN o che ha "utenti"
Perché questa separazione conta Se domani il negozio passasse da Firebase a un altro backend, cambieresti un solo file (firebase.utils.js), non dieci componenti. Questa idea ha un nome, separazione delle responsabilità: ogni livello ha un solo motivo per cambiare. Una conseguenza pratica: nessun componente dovrebbe importare direttamente da 'firebase/…'.

Il viaggio completo, livello per livello

Due varianti. Sign-up email: l'utente compila il form e preme "Sign Up". Google: l'utente preme "Google sign in". Guarda il pannello dati: a ogni passaggio di livello la forma del dato cambia.

// sign-up-form.component.jsx
const handleSubmit = async (event) => {
  event.preventDefault();

  if (password !== confirmPassword) {
    alert('passwords do not match');
    return;
  }

  try {
    const { user } = await createAuthUserWithEmailAndPassword(
      email,
      password
    );

    await createUserDocumentFromAuth(user, { displayName });
    resetFormFields();
  } catch (error) {
    if (error.code === 'auth/email-already-in-use') {
      alert('Cannot create user, email already in use');
    } else {
      console.log('user creation encountered an error', error);
    }
  }
};

const handleChange = (event) => {
  const { name, value } = event.target;
  setFormFields({ ...formFields, [name]: value });
};

// sign-in-form.component.jsx
const signInWithGoogle = async () => {
  const { user } = await signInWithGooglePopup();
  await createUserDocumentFromAuth(user);
};
Fermati e chiediti Nel passo 9 della variante sign-up, createUserDocumentFromAuth intercetta da sola gli errori di Firestore e non li rilancia. Dal punto di vista di SignUpForm, la scrittura riesce sempre. Cosa vede l'utente se le Security Rules bloccano la scrittura? Ci torniamo nelle domande da dev.

8Dalla documentazione ufficiale al codice del corso

Se apri la documentazione di Firestore non trovi createUserDocumentFromAuth. Trovi esempi con città (cities, "SF", "LA"), scritti "nudi", senza funzioni intorno. È normale: la documentazione mostra il mattone, il corso ti mostra la casa costruita con quei mattoni. Qui impari a passare dall'uno all'altra.

Lettura di un documento

DOC UFFICIALE Get data → Get a document, scheda Web (la prima: modulare)

import { doc, getDoc } from "firebase/firestore";

const docRef = doc(db, "cities", "SF");
const docSnap = await getDoc(docRef);

if (docSnap.exists()) {
  console.log("Document data:", docSnap.data());
} else {
  // docSnap.data() will be undefined in this case
  console.log("No such document!");
}

CORSO firebase.utils.js

import { doc, getDoc, setDoc } from 'firebase/firestore';

const userDocRef = doc(db, 'users', userAuth.uid);
const userSnapshot = await getDoc(userDocRef);

if (!userSnapshot.exists()) {
  // ...crea il documento con setDoc
}

return userDocRef;

DOC UFFICIALE Add data → Set a document

import { doc, setDoc } from "firebase/firestore";

await setDoc(doc(db, "cities", "LA"), {
  name: "Los Angeles",
  state: "CA",
  country: "USA"

La tabella di traduzione

Questo è il metodo per leggere qualsiasi documentazione: per ogni elemento dello snippet ti chiedi "cosa diventa nel mio dominio?".

Come nasce un'astrazione: 4 domande

1. Cosa fa lo snippet?
Descrivilo in una frase con un verbo: "legge il documento SF dalla collection cities".
2. Cosa è fisso e cosa cambia?
Quello che cambia ogni volta diventa un parametro (userAuth). Quello che è sempre uguale resta nella funzione ('users').
3. Cosa deve sapere chi chiama?
Il componente deve dare solo l'utente, non db né il percorso. Così nasce la firma: createUserDocumentFromAuth(userAuth, additionalInformation).
4. Cosa restituisco?
Cosa serve a chi chiama dopo? Un indirizzo riutilizzabile: return userDocRef.
La doc dice una cosa che il corso non dice Nella API reference di setDoc c'è scritto che "it is usually undesirable to await the Promise returned from this function". Il motivo: Firestore salva subito il dato nella cache locale (la chiama latency compensation) e lo spedisce al server appena può. La Promise però si risolve solo quando il server conferma, e se sei offline può restare in attesa a lungo. Il corso fa await setDoc(...) lo stesso: è sbagliato? Dipende da cosa ti serve. Se devi sapere che il server ha davvero accettato prima di andare avanti, l'await serve. Se vuoi che l'interfaccia non resti bloccata, no. Ecco perché conviene leggere anche la reference e non solo i tutorial: lì trovi i compromessi.

Per imparare a leggere la documentazione in generale (guide, API reference, MDN) c'è il modulo toolkit T1 · Leggere la documentazione.

9Errori tipici: dal modello sbagliato a quello giusto

Ogni errore qui sotto nasce da un'idea sbagliata. Correggere la riga non basta: va corretta l'idea, altrimenti l'errore torna in un'altra forma.

❶ "getDoc mi dà il documento"

const userSnapshot = getDoc(userDocRef);   // manca await
if (!userSnapshot.exists()) { … }          // TypeError: userSnapshot.exists is not a function

Passo per passo: getDoc parte e restituisce subito una Promise, cioè una ricevuta. La riga successiva viene eseguita immediatamente, mentre il pacco è ancora in viaggio. Chiami .exists() sulla ricevuta, e la ricevuta non ha quel metodo.

Modello sbagliato"Il codice si ferma ad aspettare a ogni riga."
Modello giusto"Le operazioni di rete restituiscono una promessa. Il codice si ferma solo dove scrivo await."

❷ "setDoc aggiorna il documento"

// documento esistente: { displayName: 'Leo', email: 'leo@mail.it', createdAt: … }
await setDoc(userDocRef, { displayName: 'Leandro' });
// adesso il documento è: { displayName: 'Leandro' }   ← email e createdAt SPARITI

Passo per passo: setDoc significa "a questo indirizzo deve esserci esattamente questo". Prende la cartella, butta via tutti i fogli e ci mette solo quello che gli hai dato.

Modello sbagliato"set = imposta questo campo."
Modello giusto"set = sostituisci la cartella intera. Per toccare solo alcuni fogli: updateDoc, oppure setDoc(…, {merge: true})."

❸ "Un campo è un pezzo del percorso"

doc(db, 'users', uid, 'displayName');
// FirebaseError: Invalid document reference. Document references must have
// an even number of segments, but users/g7Hk2/displayName has 3.

Passo per passo: conta i segmenti: sono 3, un numero dispari, quindi Firestore pensa che tu voglia una collection chiamata displayName. Ma doc() vuole un documento. Il messaggio d'errore ti sta dicendo proprio questo: leggilo, è preciso.

Modello sbagliato"Il percorso arriva fino al dato che voglio."
Modello giusto"Il percorso arriva fino al documento. I campi si leggono dopo, dalla foto: snap.data().displayName."

❹ "Se il documento non esiste, getDoc dà errore"

const snap = await getDoc(doc(db, 'users', 'nessuno'));
snap.exists();  // false   ← nessun errore
snap.data();    // undefined
{ id: snap.id, ...snap.data() }  // { id: 'nessuno' }  ← sembra un utente vero!
Modello sbagliato"Documento mancante = eccezione, la prendo nel catch."
Modello giusto"Documento mancante = foto di una cartella vuota. Va controllata con exists() prima di usare i dati."

❺ "Salvo anche la password, così ce l'ho"

await setDoc(userDocRef, { displayName, email, password });  // ✘ MAI

La password la custodisce Firebase Auth, in forma di hash, e nessuno può rileggerla, nemmeno tu. In Firestore sarebbe in chiaro, leggibile da chiunque abbia accesso al documento. Non c'è nessun caso d'uso in cui serva salvarla lì.
